## 1. 需求背景

### 1.1 行业与业务背景

口述影像（Audio Description）是一种面向视障人士的无障碍文化服务：在影视作品放映过程中，由口述员在对白间隙用语言描述画面中的视觉信息（人物动作、表情、场景变化、字幕文字等），帮助视障观众完整理解作品内容。

现场口述影像服务通常在影院、文化场馆等场地进行：大屏幕播放原片，一名或多名口述员在现场根据事先撰写的口述稿，在精确的时间点进行讲述。**口述内容必须严格卡在对白和音效的间隙中**，早一秒可能压住台词，晚一秒可能错过间隙——因此时间精度是口述影像服务质量的生命线。

### 1.2 本团队工作流特点

与传统采用文档（Word 等）撰写口述稿的方式不同，本团队采用**字幕文件形式**（如 SRT/ASS）撰写口述稿。这一工作流的核心优势在于：

- 字幕天然带有毫秒级时间轴，撰稿阶段即可在字幕软件中对照原片逐句校准，从源头保证口述稿在时间维度上的准确性；
- 现场讲述时，口述员的电脑播放带口述稿字幕的画面，字幕即提词器，口述员"见词即读"，无需自行估算时机；
- 字幕格式便于后期复用、修订与多人协作。

围绕该工作流，团队已自研配套工具**述格（ScriptGrid）**，用于将口述稿字幕文件转换为更通用的 Excel 格式，服务于审稿、存档与交换场景。本项目产品**述播（ScriptCue）**是该工具链条在**现场执行环节**的延伸。

### 1.3 现场执行的多设备架构与同步难题

一场现场口述服务涉及多台设备：

- **1 台大屏电脑**：使用本地播放器播放原片，输出至场地大屏幕，是全场时间轴的基准；
- **N 台口述员电脑**：各口述员用自己的电脑播放"原片 + 自己负责的口述稿字幕"，对照读稿。

由于团队成员技能水平和使用习惯差异较大，口述员侧的读稿方式呈现**高度异构**的状态，且短期内难以统一：

| 方式 | 使用人群 | 具体做法 |
|---|---|---|
| 硬字幕 + 本地播放器 | 初级口述员 | 将口述稿字幕烧录进原片视频，用系统自带或常用播放器播放 |
| 字幕软件直接播放 | 熟练口述员 | 将原片与字幕同时导入 Aegisub 等字幕编辑软件，在软件内播放读稿 |
| 剪辑软件预览播放 | 部分口述员 | 将原片与字幕导入剪映等剪辑工具，通过预览窗口播放读稿 |

这套架构成立的前提是：**所有电脑的播放时间轴与大屏严格一致**。只要各设备在同一时刻起播，此后各自独立播放即可基本保持同步。然而"同时起播"恰恰是目前最薄弱的环节。

### 1.4 现状做法与痛点

目前采用纯人工方式起播：所有人先将各自软件进度条拉到片头，由一人喊"1、2、3"，全体同时按下空格键。该方式存在以下问题：

1. **误差大**：人的听觉反应与按键动作差异导致各设备起播偏差普遍达数百毫秒，最差可达秒级，直接造成口述员屏幕时间与大屏时间不一致，口述时机劣化，前期字幕撰稿阶段建立的时间精度优势被现场执行环节完全抵消；
2. **不可预知、不可复现**：每次起播的误差大小和方向都是随机的，口述员无法通过固定习惯去补偿；
3. **无法核验**：起播后没有任何手段确认"到底偏了多少、谁偏了"，只能在讲述过程中凭感觉察觉，届时已影响服务质量；
4. **事故恢复成本高**：一旦发现明显不同步或放映中断，只能全体停下、重新拉进度条、重新喊口令，流程混乱且在演出现场造成不良观感；
5. **各软件起播特性不一**：不同播放器、Aegisub、剪映从"按下空格"到"画面实际动起来"的延迟各不相同，即便按键完全同步，起播仍存在系统性偏差，目前完全没有手段测量与修正。

### 1.5 前期方案论证结论

在立项前，团队已对多类方案进行论证，结论如下：

| 方案 | 结论 | 原因 |
|---|---|---|
| 统一播放软件 + Syncplay 等同步播放工具 | 不采纳 | 要求全员改变工作方式、统一软件，与团队现状（成员水平不一、习惯各异）冲突，推行阻力大 |
| LTC/MTC 专业时间码同步 | 暂不采纳 | 需专业设备与支持时间码的软件，成本与学习门槛高，同样要求改变现有工作流 |
| 局域网广播模拟按键 | 方向正确，但组网受限 | "不改变各自软件、只同步按键动作"的思路经论证可行且已有原型验证；但现场各设备**难以保证接入同一局域网**（场地网络条件不一、设备可能分别使用手机热点/场馆 WiFi/有线网络） |
| **公网服务 + 绝对时刻调度触发按键** | **本项目采用** | 保留"同步按键"思路，将指令通道从局域网升级为公网，通过时钟对齐与绝对时刻调度消除公网延迟抖动的影响，各设备可各自以任意方式接入互联网 |

### 1.6 产品定位

述播（ScriptCue）定位为团队口述影像工具链中的**现场执行同步工具**，与述格（ScriptGrid，撰稿/转换环节）形成互补，共同构成 "Script" 产品家族，覆盖"撰稿 → 现场执行"的完整链路。

产品名释义：**Cue** 为演出与广播行业术语，意为"提示信号、开始指令"（即导演口令 "Standby... Cue!"），与本产品"下发同步起播指令"的核心功能高度吻合，亦暗合口述影像的现场演出场景。

产品设计遵循两条核心原则：

1. **零侵入**：不要求口述员改变任何现有读稿软件和习惯，同步能力以"外挂"形式叠加在现有工作流之上；
2. **低门槛**：主控端为免安装网页，被控端为免安装单文件程序，非技术背景成员经一次培训即可独立使用。

### 1.7 目标用户与使用规模

- 本团队及同类口述影像公益/服务团队；
- 单场演出设备规模：1 台大屏电脑 + 1~19 台口述员电脑；
- 使用频率：按演出场次，典型为每周至每月数场；
- 用户技术背景：普遍为非技术人员，包含使用 macOS 与 Windows 的混合群体。

## 2. 产品目标与成功指标

| 目标 | 指标 |
|---|---|
| 起播同步精度 | 全体设备触发时刻偏差 **≤ 50ms**（目标 ≤ 20ms） |
| 易用性 | 口述员侧操作 ≤ 3 步：启动客户端 → 输入房间码 → 就位等待 |
| 可靠性 | 单场演出（3 小时）内客户端与服务器连接保持率 ≥ 99.9%，断线自动重连 |
| 兼容性 | 被控端支持 Windows 10+ 与 macOS 12+；主控端支持主流手机/电脑浏览器 |

## 3. 术语定义

| 术语 | 定义 |
|---|---|
| 主控端 | 运行在手机/电脑浏览器中的控制网页，由现场导控人员操作 |
| 被控端 | 安装在大屏电脑及各口述员电脑上的客户端程序，负责模拟按键 |
| 房间 | 一场演出对应一个房间，用 6 位房间码标识，所有设备加入同一房间 |
| 触发 | 被控端向前台窗口模拟按下空格键的动作 |
| 补偿值 | 针对每台设备所用软件起播延迟的毫秒级修正量，可正可负 |
| 时钟偏移 | 被控端本地时钟与服务器时钟的差值，由客户端持续估算 |

## 5. 系统架构总览

```
                        公网（互联网）
                             │
                    ┌────────┴────────┐
                    │  ScriptCue 服务器│
                    │ · WebSocket 服务 │
                    │ · 房间管理       │
                    │ · 授时基准       │
                    └────────┬────────┘
        ┌──────────┬─────────┼─────────┬──────────┐
        │          │         │         │          │
   ┌────┴───┐ ┌────┴───┐ ┌───┴────┐ ┌──┴─────┐ ┌──┴─────┐
   │ 主控端  │ │ 被控端  │ │ 被控端  │ │ 被控端  │ │ 被控端  │
   │手机网页 │ │大屏电脑 │ │口述员A │ │口述员B  │ │口述员C │
   └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
```

**同步核心机制（本产品最关键的设计，开发必读）**：

公网延迟高且抖动大（10~300ms 不等），**绝不能**采用"收到指令立即触发"的模式。必须采用**"时钟对齐 + 绝对时刻调度"**：

1. 每个被控端加入房间后，持续与服务器做时钟同步（类 NTP 算法）：发送 ping，记录本地发出时间 t0、服务器时间 ts、本地收到时间 t1，估算偏移 = ts − (t0+t1)/2。多次采样，**取 RTT 最小的样本**作为可信偏移，精度可达 10~20ms；
2. 主控发出起播指令时，服务器广播的内容是："请在服务器时间 T（= 当前 + 3 秒）触发"；
3. 各被控端将 T 换算为本地时钟时刻（T − 自己的偏移 − 自己的补偿值），本地高精度定时到点触发；
4. **这样网络延迟和抖动只要不超过 3 秒的提前量，就完全不影响同步精度**；精度只取决于时钟偏移估算质量。

## 6. 功能需求

### 6.1 云端服务

| 编号 | 功能 | 描述 | 优先级 |
|---|---|---|---|
| S-01 | 房间管理 | 主控端创建房间，生成 6 位房间码 + 可选口令；房间空闲 24h 自动销毁 | P0 |
| S-02 | WebSocket 长连接 | 维护主控端与全部被控端的长连接，心跳间隔 5s，3 次无响应判定离线并通知主控 | P0 |
| S-03 | 授时服务 | 响应被控端的时钟同步请求，返回高精度服务器时间戳（毫秒级） | P0 |
| S-04 | 指令广播 | 将主控端指令（起播/暂停/测试/取消）附加"执行时刻 T"后广播给房间内所有被控端 | P0 |
| S-05 | 状态汇聚 | 收集各被控端心跳中携带的状态（在线、时钟同步质量、就绪标记、最近触发结果），推送给主控端 | P0 |
| S-06 | 多房间隔离 | 支持多场演出并行，房间间指令与状态完全隔离 | P1 |
| S-07 | 操作日志 | 记录每次指令下发与各端触发回执，供演出后复盘 | P1 |

### 6.2 主控端（响应式网页，适配手机竖屏优先）

| 编号 | 功能 | 描述 | 优先级 |
|---|---|---|---|
| C-01 | 创建/进入房间 | 输入房间名创建，或输入房间码进入既有房间 | P0 |
| C-02 | 设备列表 | 实时显示房间内所有被控端：设备昵称、在线状态、时钟同步质量（优/良/差，按偏移估算的置信区间分级）、就绪状态、补偿值 | P0 |
| C-03 | 全体起播按钮 | 大号醒目按钮；点击后弹出二次确认；确认后下发"3 秒后触发"指令，页面显示倒计时 | P0 |
| C-04 | 全体暂停/恢复 | 同样以"绝对时刻调度"方式下发（空格键本身即播放/暂停切换，被控端动作相同） | P0 |
| C-05 | 触发回执展示 | 起播后各设备回报"实际触发时刻"，主控页面显示每台设备与目标时刻的偏差（ms），异常标红 | P0 |
| C-06 | 单设备测试触发 | 对指定单台设备下发测试指令，用于演出前逐台验证按键是否生效 | P0 |
| C-07 | 全体测试触发 | 演出前彩排用，流程同正式起播但界面标记为测试 | P1 |
| C-08 | 远程调整补偿值 | 主控可查看并修改任一被控端的补偿值（免去逐台电脑上手改配置） | P1 |
| C-09 | 指令取消 | 倒计时期间可取消尚未执行的指令 | P1 |
| C-10 | 防误触 | 起播/全体测试按钮需点击后弹框二次确认；房间口令校验 | P1 |

### 6.3 被控端（桌面客户端，Windows / macOS）

| 编号 | 功能 | 描述 | 优先级 |
|---|---|---|---|
| R-01 | 加入房间 | 启动后输入房间码、口令、设备昵称（如"口述员-小王-剪映"），昵称记忆 | P0 |
| R-02 | 时钟同步 | 加入房间后立即密集采样（20 次）估算时钟偏移，之后每 30 秒维持性采样；向服务器上报同步质量 | P0 |
| R-03 | 定时触发按键 | 收到指令后按"执行时刻 T − 时钟偏移 − 补偿值"本地调度，到点向前台窗口模拟按下空格键 | P0 |
| R-04 | 触发回执 | 触发后立即回报实际执行时刻（换算为服务器时钟），供主控端展示偏差 | P0 |
| R-05 | 本地补偿值配置 | 客户端界面可设置补偿值（毫秒，支持正负），并接受主控端远程修改（C-08） | P0 |
| R-06 | 就绪标记 | 口述员将播放软件就位后，点击客户端"我已就绪"按钮，状态同步到主控端 | P0 |
| R-07 | 断线重连 | 网络中断后自动重连并重新时钟同步；重连期间界面明显提示 | P0 |
| R-08 | 触发前提示音 | 执行时刻前 3 秒起，客户端播放"滴、滴、滴"倒数提示音，提醒口述员手离键鼠 | P1 |
| R-09 | 窗口置顶小面板 | 客户端以小尺寸置顶窗口显示：连接状态、就绪状态、倒计时；不遮挡读稿区域，可拖动 | P1 |
| R-10 | macOS 权限引导 | 首次运行检测辅助功能权限，未授权时弹出图文引导（直达系统设置对应页面） | P0 |
| R-11 | 开机自检 | 启动时自测模拟按键能力（向自身窗口发键验证），失败则明确报错 | P1 |
| R-12 | 焦点保护（进阶） | 可选配置目标窗口（按窗口标题匹配），触发时先激活该窗口再发键，降低误触其他窗口的风险 | P2 |

> **关于焦点问题的说明**：V1 以"提示音 + 操作规范（就绪后手离键鼠）"为主要保障，R-12 作为 P2 进阶项，因跨平台指定窗口发键的实现复杂度较高（macOS 需借助 AppleScript/Accessibility API，各软件行为不一）。

## 7. 核心流程

### 7.1 演出前准备流程

```
导控：手机打开述播主控网页 → 创建房间 → 将房间码告知全员
  │
各口述员/放映员：启动述播被控客户端 → 输入房间码+昵称 → 客户端自动时钟同步
  │
导控：确认设备列表全部在线、时钟质量为"优"
  → 逐台"单设备测试触发"验证按键生效（C-06）
  → （可选）全体测试触发一次，核对偏差回执，微调补偿值
  │
各口述员：打开自己的播放软件 → 进度归零 → 窗口置前台 → 点击"我已就绪" → 手离键鼠
  │
导控：看到全员就绪 → 点击“全体起播”并弹框确认 → 3 秒倒计时 → 全体同步触发
```

### 7.2 起播指令时序

```
主控端          服务器            被控端×N
  │  起播请求      │                 │
  │──────────────▶│                 │
  │               │ 计算 T=now+3000ms│
  │               │  广播{PLAY, T}   │
  │               │────────────────▶│
  │  ◀─倒计时同步──│                 │ 本地换算：T-偏移-补偿
  │               │                 │ 高精度定时等待
  │               │                 │ ══到点，模拟空格══
  │               │  ◀──触发回执─────│
  │ ◀─偏差汇总─────│                 │
```

### 7.3 演出中事故处理流程

大屏卡顿/需要重来 → 导控下发"全体暂停" → 各口述员按大屏实际位置手动拖动自己软件的进度条对位 → 各自重新点"就绪" → 导控再次"全体起播"（此时空格恢复播放）。

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 同步精度 | 触发时刻标准差 ≤ 20ms；最大偏差 ≤ 50ms（不含各软件起播延迟，该部分由补偿值消除） |
| 定时精度实现要求 | 被控端定时不得使用普通 sleep 到点（OS 调度误差可达 15ms+），须采用"粗睡眠 + 最后 50ms 自旋等待"策略 |
| 网络容忍 | 单程延迟 ≤ 1s 的网络环境下功能不受影响；指令提前量默认 3s，可配置 |
| 服务器性能 | 单房间 ≤ 20 连接、并发 ≤ 10 房间；1 核 1G 云主机即可承载 |
| 安全 | 全链路 WSS/HTTPS；房间口令校验；指令仅主控端可发；不采集除设备昵称外的任何个人信息 |
| 可用性 | 客户端断线自动重连（指数退避，上限 10s）；服务器无状态设计目标，重启后客户端可自动恢复房间 |
| 分发 | 被控端打包为免安装单文件（Windows .exe / macOS .app），无需用户安装 Python 等环境 |

## 9. 技术选型建议（供开发参考，非强制）

| 组件 | 建议 | 理由 |
|---|---|---|
| 服务器 | Python (FastAPI + websockets) 或 Node.js | 轻量、开发快 |
| 主控端 | 纯网页（Vue/React 或原生 JS），响应式布局 | 免安装、跨平台，避开 APP 上架审核 |
| 被控端 | Python + pynput + PyInstaller 打包；界面用 tkinter/PyWebview | 延续已验证的按键方案，跨平台成本最低 |
| 部署 | 单台云主机 + 域名 + SSL 证书 | 成本低，满足规模需求 |

## 10. 验收标准（关键场景）

1. **精度验收**：3 台 Windows + 2 台 macOS 分别通过手机热点、有线宽带、场馆 WiFi 混合接入公网，全体起播 20 次，用 240fps 慢动作录像逐帧核对，触发偏差全部 ≤ 50ms；
2. **断线恢复**：起播指令倒计时期间拔掉一台被控端网线——该设备应错过触发且主控端明确标红告警；恢复网络后 15 秒内自动重连并可参与下次触发；
3. **时钟漂移**：被控端连续运行 4 小时后再次触发，偏差仍满足精度要求（验证维持性时钟采样有效）；
4. **macOS 权限**：全新 Mac 首次运行，权限引导流程可让非技术用户 3 分钟内完成授权；
5. **异构软件**：分别用 VLC、Aegisub、剪映作为前台软件各测试 10 次触发，配置补偿值后画面起播偏差 ≤ 100ms。

## 12. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 现场公网质量极差（大延迟抖动） | 中 | 架构上已通过绝对时刻调度免疫抖动；极端断网时保留"NTP 校时 + 约定时刻"离线降级模式（P2 备选功能） |
| macOS 权限被系统更新重置 | 中 | 每次启动自检（R-11），失败即显著告警 |
| 口述员误触焦点窗口 | 中 | 提示音 + 就绪流程规范；P2 实现指定窗口发键 |
| 剪映等软件预览掉帧导致播放中漂移 | 中 | 本系统只保证"起播同步"；播放中漂移属软件特性，建议配合"大屏时间参考窗"（列入 V2）并逐步引导口述员迁移到播放器方案 |
| 长片中途无重新对位手段 | 低 | V2 规划"定点同步"：约定在某时间码处全体暂停再同步恢复 |
